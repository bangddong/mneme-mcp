# 프로젝트 연동 가이드 — raw 데이터를 쌓는 프로젝트가 mneme/위키를 활용하는 법

> **대상 독자**: 자기 repo에 raw 데이터·코드를 쌓으면서,
> 그 과정에서 생기는 지식을 위키로 축적·재사용하고 싶은 프로젝트 (사람 + 그 프로젝트의 Claude 에이전트).
> 설치 명령만 필요하면 [PLAYBOOK.md](PLAYBOOK.md) §8, 호출 규약 원문은 `integration/CLAUDE-mneme.md.template`.
> 이 문서는 **허브(mneme) 관점**이다. 소비 프로젝트 담당자용 가이드는 위키에 있다
> — `wiki/guide/pages/project-onboarding.md` ("우리 지식도 저 위키에 쌓고 싶은데?" 할 때 보는 문서).

---

## 1. 개념 지도 — 데이터는 네 곳으로 나뉜다

연동의 핵심은 도구 호출이 아니라 **"무엇을 어디에 두는가"**다.

```
[프로젝트 repo]          [위키 <카테고리>/]        [mneme 스킬]           [mneme 에피소드]
 raw 데이터·코드·설정  →  정제된 지식 (OKF)        역량 숙련도 (θ_eff)     작업 이력·반성
 프로젝트 소유            모든 에이전트 공유 자산    성장 상태               경험 로그
```

| 저장소 | 무엇을 | 왜 거기에 |
|--------|--------|-----------|
| **프로젝트 repo** | raw 데이터, 코드, 설정, 프로젝트 전용 문서(README/docs/ADR) | 그 프로젝트 안에서만 의미. git이 이력 관리 |
| **위키 `<카테고리>/`** | 프로젝트를 *넘어* 유용한 정제 지식 (개념·패턴·교훈) | 다른 프로젝트·미래 세션·다른 에이전트가 재사용. OKF라 이식 가능 |
| **mneme 스킬** | 반복 역량의 숙련도 (`<prefix>` 접두 스킬) | 세션이 리셋돼도 "얼마나 잘하게 됐나"가 누적. degrading 시 복습 알림 |
| **mneme 에피소드** | 매 작업의 결과·반성 (`episode_reflect`) | 스킬 성향 학습의 원료 + "누가 뭘 했나" 감사 로그 |

**제1원칙: raw는 프로젝트에, 지식은 위키에, 진척은 스킬에, 이력은 에피소드에.**
위키는 데이터 레이크가 아니다 — 정제를 거친 것만 승격한다 (§4).

관련 설계 원칙 (DECISIONS.md):
- **읽기=직접**: 다른 에이전트가 위키 지식을 쓸 땐 마크다운을 직접 읽는다 (약한 LLM 경유 금지).
- **런타임 연동 금지**: 앱 코드가 mneme를 호출하지 않는다. 연동 주체는 **에이전트(개발 세션)와 빌드타임 배치**뿐 (07-02 #3).

## 2. 연동 절차 (1회, ~5분)

```bash
# 1) 설치 스크립트 (멱등 — .mcp.json 머지 + CLAUDE.md 규약 블록)
cd E:/development/mneme-mcp
python integration/install.py --project <프로젝트경로> \
    --agent <에이전트명> --category <위키카테고리> --prefix <스킬접두어->

# 2) 위키 카테고리 생성 (없으면)
#    기존 카테고리(예: wiki/tech/) 구조 복사: CLAUDE.md + index.md + log.md + pages/ + sources/
#    위키 루트 index.md·CLAUDE.md 표에 행 추가

# 3) Claude Code 재시작 → 해당 프로젝트에서 mneme_status 호출로 확인
```

네이밍 관례 (예시 프로젝트 `myapp`):

| 인자 | 규칙 | 예시 값 |
|------|------|--------|
| `--agent` | `<프로젝트약칭>-<역할>` — episodes.agent에 기록돼 "누가 한 일"인지 식별 | `myapp-builder` |
| `--category` | 위키 디렉토리명 = 프로젝트명 | `myapp` |
| `--prefix` | 스킬 이름 접두어 (학습 스킬 `study-`와 구분) | `myapp-` |

## 3. 세션 수명주기 — 프로젝트 에이전트의 호출 규약

CLAUDE.md 블록에 설치되는 표의 "언제·왜" 해설판.

```
세션 시작 ──▶ 작업 계획 ──▶ 작업 중 ──▶ 작업 종료
growth_log()   skill_suggest   wiki_search    episode_reflect
(조치 확인)     (교훈 회수)      (지식 재사용)    (경험 적립)
                                wiki_inject
                                (지식 승격)
```

| 시점 | 호출 | 하는 일 |
|------|------|---------|
| 세션 시작 | `growth_log()` | 자기평가가 쌓아둔 조치 항목 확인. 이 프로젝트 스킬 관련이면 해소 |
| 작업 계획 | `skill_suggest(task, session_id)` | 관련 스킬 성향 + 과거 에피소드 교훈(next_hint)을 계획에 반영 |
| 막힐 때/조사 전 | `wiki_search(query, session_id, agent=...)` | **먼저 검색** — 과거에 정리해둔 지식이 있으면 재조사 대신 재사용. 자기 카테고리 밖(tech/ 등)도 걸린다 |
| 지식이 생겼을 때 | `wiki_inject(path, content, source_agent=..., session_id)` | §4 승격 기준 통과분만. OKF 페이지 형식 준수 |
| 새 반복 역량 | `skill_seed("<prefix>-<역량>", description)` | 예: `myapp-batch-pipeline`. 일회성 작업엔 만들지 않는다 |
| 작업 종료 | `episode_reflect(task, outcome, success, score, skills_used, session_id, agent=...)` | 성공=성향↑ / 실패=성향↓. **skills_used에 스킬명을 넣어야 학습된다** |

- `session_id`: 세션마다 고정 문자열 하나 (예: `myapp-20260703`).
- `agent`: 항상 자기 이름. 빠뜨리면 `unknown`으로 박제돼 옵저버빌리티가 죽는다.
- 서버가 꺼져 있으면 도구가 안 보임 → **무시하고 평소대로** (선택적 의존).

## 4. 승격 기준 — 무엇이 위키로 가는가

`wiki_inject` 전에 3문을 통과시킨다:

1. **이 프로젝트가 끝나도 유효한가?** (프레임워크 개념·패턴·일반 교훈 → Yes)
2. **다른 프로젝트/에이전트/미래의 내가 검색해서 쓸 장면이 그려지는가?**
3. **repo 문서가 더 맞는 자리 아닌가?** (코드 구조·설정법·프로젝트 결정 → repo의 README/docs/ADR)

| 예시 | 행선지 |
|------|--------|
| "JWT refresh 로테이션 전략 비교·선택 근거" | 위키 `tech/pages/` 또는 `<카테고리>/pages/` (개념) |
| "우리 서비스의 JWT 만료 30분 설정과 그 이유" | repo docs (프로젝트 결정) |
| 크롤링한 원문 JSON 1만 건 | repo (raw 데이터 — 위키 반입 금지) |
| 원문 1만 건을 분석해 뽑은 "상위 패턴 분석" | 위키 (정제된 지식) |
| 오늘 디버깅하다 삽질한 얘기 | 에피소드(`episode_reflect`)로만 — 위키 아님 |

**raw → 위키 파이프라인**: raw는 repo에 계속 쌓고, **정제 시점**(마일스톤·배치·"이제 정리하자" 세션)에
에이전트가 raw를 분석해 결과만 `wiki_inject`. 실시간 동기화하지 않는다.

## 5. 유스케이스

### UC1. 개발 중 조사한 지식의 복리 축적 (기본 루프)
연동 프로젝트에서 QueryDSL N+1 문제를 조사해 해결했다 →
① 해결 즉시 `wiki_inject("tech/pages/java-spring/querydsl-n-plus-one.md", ...)`
② `episode_reflect(skills_used=["myapp-jpa-tuning"], ...)`
③ 두 달 뒤 다른 프로젝트에서 같은 문제 → `wiki_search("QueryDSL N+1")` 한 방에 회수.
**조사 비용을 두 번 내지 않는 것**이 이 시스템의 존재 이유.

### UC2. raw 데이터 → 빌드타임 시드 (질문 뱅크 패턴)
위키에 쌓인 tech/·ai-llm/ concept 페이지를 훑어 소비 프로젝트의 질문 뱅크 테이블 시드 데이터 PR을 만든다.
- 방향: **위키 → 프로젝트** (읽기=직접 — 에이전트가 마크다운을 직접 읽고 변환)
- 시점: **빌드타임만**. 앱이 런타임에 mneme를 호출하는 구조는 금지 (DECISIONS 07-02 #3)
- 프롬프트 예: PLAYBOOK §8 "질문 뱅크 채우기"
일반화: *위키의 정제 지식을 프로젝트의 정적 자원(시드·fixture·문서)으로 컴파일*하는 모든 경우.

### UC3. 프로젝트 도메인 지식 카테고리 (`<카테고리>/pages/`)
프로젝트 고유지만 세션을 넘어 유효한 도메인 지식 — 예: "직군별 요구 기술 스택 분석",
"질문 유형 분류 체계". 코드가 아니라 **도메인 이해**라 repo docs보다 위키가 맞고,
카테고리를 분리해 tech/(범용 기술)와 섞이지 않게 한다. 크로스 참조는 위키 루트 절대경로 링크.

### UC4. 반복 역량의 성향 추적 + 복습 알림
프로젝트에서 반복되는 작업 유형(예: `myapp-batch-pipeline`, `myapp-api-design`)을 스킬로 등록하고
매 작업 후 `episode_reflect` → 성공률이 성향에 누적 → Outer Loop이 승급/강등 →
한동안 안 쓰면 degrading → **Discord 웹훅으로 복습 알림**. 학습 스킬(`study-`)과 동일 메커니즘이
프로젝트 역량에도 적용된다.

### UC5. 크로스 프로젝트 지식 재사용
새 프로젝트 B가 시작되면 install.py로 연동하는 순간 A가 쌓아둔 전 카테고리를 `wiki_search`로
검색할 수 있다. 카테고리는 소유 경계(누가 주로 쓰나)지 접근 경계가 아니다.
→ 프로젝트가 늘수록 두뇌가 좋아지는 구조.

## 6. 안티패턴

| 하지 말 것 | 왜 |
|-----------|-----|
| 앱 런타임 코드에서 mneme 호출 | 앱이 로컬 서버에 결합됨. 연동 주체는 에이전트·빌드타임뿐 (DECISIONS 07-02 #3) |
| raw 데이터를 통째로 `wiki_inject` | 위키는 정제 지식. raw는 repo에 (§4) |
| 프로젝트 설정·코드 구조 문서를 위키에 | repo CLAUDE.md/docs가 자리. 위키는 프로젝트가 죽어도 남을 것만 |
| `agent`/`skills_used` 생략 | 이력이 `unknown`으로 박제되고 스킬 학습이 안 됨 |
| 일회성 작업에 `skill_seed` | 스킬은 반복 역량. 일회성은 에피소드로 충분 |
| 위키 검색 없이 재조사부터 시작 | UC1의 복리를 스스로 버리는 것. **검색 먼저** |
| mneme 다운 시 작업 중단 | 선택적 의존 — 도구 없이 평소대로 진행 |

## 7. 연동 상태 점검 체크리스트

프로젝트에서 Claude Code를 열고:

- [ ] `mneme_status()` 응답 오는가 (안 오면 서버 다운 — PLAYBOOK §7)
- [ ] CLAUDE.md에 "## mneme" 블록이 있고 agent/카테고리/접두어가 치환돼 있는가
- [ ] `wiki_list(prefix="<카테고리>")`에 카테고리가 보이는가
- [ ] `episode_log`(또는 `python -m mneme.log -a <에이전트명>`)에 이 프로젝트 이력이 쌓이고 있는가
- [ ] `skill_suggest`가 `<prefix>` 스킬을 돌려주는가 (없으면 아직 seed 안 한 것 — 정상일 수 있음)
